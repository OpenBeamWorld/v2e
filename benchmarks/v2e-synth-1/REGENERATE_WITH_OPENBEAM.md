# Regenerating v2e-synth-1 with OpenBeam renders

Status: **planned, not run.** In the first release every v2e-synth-1 clip is generated offline:
the `fake` connector simulates each case and the in-package ray caster
(`openbeam_v2e.reconstruct.render`) draws the frames. This page describes how the same cases are
regenerated from engine renders later, using only the documented OpenBeam MCP tools, so anyone
with an OpenBeam account can reproduce the truth with their own session.

Nothing on this page needs private tools, private settings or a special build. Tool names and
arguments are those of OpenBeam's published MCP tool reference at the time of writing (see the
connection guide at [openbeam.world](https://openbeam.world/docs/connect-openbeam-to-codex-or-claude/));
check your session's `tools/list` before running anything, since game versions differ.

## What changes and what stays

| | Offline (first release) | OpenBeam renders (planned) |
| --- | --- | --- |
| Case definitions | `openbeam_v2e.bench.families` | the same, unchanged |
| Content | generic vehicle and props from the V2E generators | the same content, compiled with the OpenBeam dialect |
| Physics | `fake` connector (rigid test double) | OpenBeam soft-body physics in stepped mode |
| Frames | in-package ray caster | `camera_frame` after every rendered frame's worth of steps |
| Claim class | `test_double` | `native` |
| Label | synthetic self-consistency | synthetic self-consistency (engine-rendered) |

Every figure from either kind of truth is a self-consistency figure: the truth is a simulated
run, so it supports no claim about accuracy on real footage. Accuracy claims come only from the
real clips with independent measurements (planned for a later release).

## Steps

The generator is the same code path as offline generation, with the OpenBeam connector in place
of `fake`:

```sh
openbeam-v2e bench synth generate --backend openbeam --subset full --out v2e-synth-1-openbeam/
```

That command is not wired in the first release. When it is, it performs these documented calls
per case:

1. **Session.** `cloud_session_start` with `{"kind": "training"}`: stepped physics is available
   only in training sessions. A local game is used through its own MCP endpoint instead.
2. **Content.** Compile the case (`openbeam-v2e compile`) and install the packages:
   `upload_level` for the level archive, `install_mod` for each vehicle and prop archive, each
   with a URL you control and the archive's SHA-256.
3. **Scene.** `load_level`, then spawn every actor at rest at its spawn pose (`spawn_vehicle`,
   or the connector's documented spawn path), and read the actual poses back with `actor_poses`.
   Stepped mode needs a player vehicle, so props-only cases (`drop_and_bounce`) add an
   off-camera anchor vehicle that counts toward the vehicle limit and is never scored.
4. **Stepped run.** `sim_mode` with `{"mode": "stepped"}`; then, for each delivered frame,
   `sim_step` by the number of 0.5 ms physics steps in one frame interval and `camera_frame`
   to grab the frame. Controller programs run in the connector's engine-side host.
5. **Truth.** Poses come from the connector's run log in the `v2e-runlog/1` format; events are
   detected from the poses and the case geometry exactly as offline.
6. **Close.** `sim_mode` with `{"mode": "realtime"}` and `cloud_session_end` for the session the
   generator started.

## Release checks before publishing engine-rendered truth

- Truth tables regenerate within the benchmark's repeatability tolerances in stepped mode
  (median over nine runs; position 1 mm, angle 0.1 deg, time one step resolution floors).
- Frames are compared perceptually against the release (PSNR at least 40 dB); stream encodes are
  never compared by hash.
- Container metadata and encoder build strings are stripped from every published video.
- Every render-visible asset is generated by V2E or openly licensed, and listed in the
  provenance record next to the clip.
